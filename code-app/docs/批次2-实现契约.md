## 0. 范围与完成标志

**批次 2 = 门诊业务流全链路**：挂号 → 接诊 → 四诊 → 辨证 → 开方 → 提交送审 → 药师审核 → 调剂 → 发药（含作废分派与随访自动生成）。

| 屏幕 | 协议 | 聚合 | 本批行为（MU 动作） |
|---|---|---|---|
| UI-02 门诊挂号 `frmVisitRegister` | SINGLE_FORM | `AGG-VISIT-001` | `Visit_Register`(`actSave`)、`Visit_Cancel`(`actCancelVisit`) |
| UI-03 接诊开单 `frmVisitReceive` | SINGLE_FORM | `Visit` | `Visit_Receive`(`actSave`) |
| UI-04 四诊录入 `frmFourDiagnosis` | SINGLE_FORM | `Visit`(+`FourDiagnosis`) | `Visit_SaveFourDiagnosis`(`actSave`) |
| UI-05 辨证判定 `frmDiagnosisJudge` | MASTER_DETAIL_FORM | `AGG-DIAGNOSIS-001` | `Diagnosis_Save`(`actSave`)、`Diagnosis_Confirm`(`actConfirm`) |
| UI-06 开具处方 `frmPrescription` | MASTER_DETAIL_FORM | `AGG-PRESCRIPTION-001`(+`PrescriptionItem`) | `Prescription_Save`(`actSaveDraft`)、`Prescription_Submit`(`actSubmit`) |
| UI-07 处方审核 `frmPrescriptionReview` | SINGLE_FORM | `Prescription` | `Prescription_Review`(`actApprove`/`actReject`) |
| UI-08 调剂发药 `frmDispense` | MASTER_DETAIL_FORM | `AGG-DISPENSE-001` | `Dispense_Confirm`(`actConfirmDispense`)、`Dispense_Issue`(`actIssue`) |

**本批同时实现 6 个系统自动行为**（无界面，由链路触发）：`Visit_Complete`、`FollowUp_CreatePlan`、`Dispense_CreatePending`、`Dispense_CancelPending`、`Herb_DeductStock`、`Herb_ReturnStock`。

**接口外行为**：`Prescription_Cancel`（处方退回与作废）— MU 中其动作 `actVoid` 位于 **UI-19「就诊与处方记录查询」屏**（属批次 3）；本批**实现后端行为 + 接口 + R-04 分派**并纳入验收，界面留批次 3 接入。不得在本批擅自给其他屏加作废按钮（有违 MU）。

**完成标志**：① 全链路（挂号→接诊→四诊→辨证→开方→提交→审核→调剂→发药）在真实 HTTP 上跑通；② R-01～R-05 真实生效（含负例）；③ 作废三分派（VOID_ONLY / VOID_WITH_ROLLBACK / BLOCK）可验证；④ 库存在调剂/回冲后与流水净和一致（INV-03/R-06）；⑤ 权限与菜单可见性符合 M5；⑥ 前端构建通过。

**本批不做**：6 个统计报表屏（含 `QR-VISIT-PRESCRIPTION-001` 与超量台账，批次 3）、随访登记屏与随访分析（批次 3）、AI 对话框（批次 3）、子流程调用（引擎本期不实现）。

## 7. 前端页面契约

**逐元素、逐动作、ASCII 布局一律以 `docs/批次2-屏幕规格（MU抽取）.md` 为准**（该文件由 MU 直接抽取生成，含 7 屏共 94 个元素、12 个动作）。实现要求：

## 8. 规则与联动编排（本批核心，必须逐条真实生效）

### 8.1 M3 规则落地（`services/domain_rules.py`，供处方/调剂服务调用）

| 规则 | 判定与落地 | 失败提示（中文，逐字使用） |
|---|---|---|
| **R-01** 剂量超量 `RULE-PRESCRIPTION-DOSE-LIMIT-CHECK` | 逐味：`singleDose <= maxCommonDose` → PASS；`singleDose > maxCommonDose * 2` → **BLOCK（阻断保存）**；否则 → **NEED_REASON**（必须填 `over_dose_reason`，否则阻断保存/提交） | 阻断：「`X` 单剂剂量 `N`g 超过常用最大量 `M`g 的 2 倍，禁止开具」；需理由：「`X` 单剂剂量 `N`g 超过常用最大量 `M`g，请填写超量理由」 |
| **R-02** 库存充足 `RULE-HERB-STOCK-SUFFICIENT` | 逐味：`singleDose * doses > herb.stockQuantity` → 不充足；**调剂确认前**必须全部充足 | 「`X` 需求 `R`g 超过库存 `S`g，无法调剂」 |
| **R-03** 毒性总量上限 `RULE-HERB-TOXIC-TOTAL-LIMIT-CHECK` | 对 `toxicityLevel != 'NONE'` 且在处方中出现的饮片：该味在处方中的**单剂总量**（=`singleDose`）`<= toxicDoseLimit`；`toxicDoseLimit` 为空表示不单独设限（放行）。**判定阶段 = 提交送审**（M3 `reusedBy: [Prescription_Submit]`）：保存草稿不因毒性总量阻断 | 「毒性饮片 `X` 单张处方总量 `T`g 超过上限 `L`g」 |
| **R-04** 作废分派 `RULE-PRESCRIPTION-VOID-DISPATCH` | 依调剂发药记录状态：无记录或 `PENDING` → `VOID_ONLY`；`DISPENSED` → `VOID_WITH_ROLLBACK`；`ISSUED` → `BLOCK`（阻断作废） | 阻断：「处方已发药，不可作废」 |
| **R-05** 复诊日期顺序 `RULE-FOLLOWUP-DATE-ORDER` | `actualFollowUpDate >= DATE(sourceVisit.registerTime)` | 「实际随访日期不得早于上次就诊挂号日期」 |
| R-06 库存对账 | 批次 1 已实现，本批在调剂/回冲后必须继续成立（`stock_quantity == SUM(herb_stock_flow.quantity)`） | 复用批次 1 文案 |

> 规则函数签名建议：`domain_rules.check_prescription_items(items, herb_map) -> list[dict]`、`check_stock_sufficient(items, doses, herb_map)`、`check_toxic_total(items, herb_map)`、`dispatch_on_cancel(dispense_record) -> str`、`check_followup_date_order(actual_date, register_time)`。规则要么返回判定结果，要么 `raise ValueError(中文)`，**不得静默放行**。

### 8.2 事务边界

- **一个行为 = 一个事务**（`db.transaction(fn)`），聚合内主从同事务。
- **跨聚合联动在同一事务内完成**（本批链路均为强一致）：处方提交链、审核通过链、调剂链、作废链、就诊完成链、随访生成链。任一步失败 → 整体回滚并抛中文异常。
- 不允许「先提交事务再异步补写」的实现方式。

### 8.3 处方提交链（`Prescription_Submit`，单事务）

```
1) 处方状态 → PENDING_REVIEW，写 submit_time（业务行为）
2) 引擎启动审批流实例：FlowEngine(conn).get_definition_by_code("FLOW-PRESCRIPTION-APPROVAL-001")
   → engine.start(def_id, business_key=f"处方{prescription_no}", business_object_refs=[{...}],
                  variables={"prescriptionId":..., "patientId":..., "doses":..., "hasOverDose": bool},
                  creator_id=当前用户 id)
   说明：M6 审批流已由 seed 落库（7 节点 7 边）；审批任务角色为中药师（ROLE-03），任务出现在「我的待办」
3) 联动 Visit_Complete（syncTriggers）：visit_service.complete_visit(visit_id, conn) → 就诊置 COMPLETED
4) 联动 FollowUp_CreatePlan：followup_service.create_plan(patient_id, visit_id,
      planned_date = DATE(visit.register_time) + doses 天, conn)   # D-17：就诊日期 + 剂数天
   幂等：同一 source_visit_id 已存在随访记录则直接返回既有记录（不重复生成）
```
> 引擎的 `system_task` 节点**不会**自动调用业务行为（引擎只记账），因此上述业务动作必须由 `prescription_service` 显式编排。

### 8.4 审核与作废链

- `Prescription_Review(APPROVE)`：状态 → `APPROVED`（+`reviewer_id/review_time`）→ **Dispense_CreatePending**：生成 `dispense_record`（`FY+6`、`record_status=PENDING`、`dispense_time` 先置为创建时间，`dispenser_id` 暂填当前审核人？**否** → 按 M1 必填约束，`dispenser_id` 在创建时填占位 `""` 不允许，故**创建时写入当前审核用户 id**，调剂确认时覆盖为实际调剂人）→ 若存在该实例的待办任务（`flow_task.status='TODO'`）则 `engine.approve(...)` 结束流程；幂等：该处方已有 `dispense_record` 时不重复创建。
- `Prescription_Review(REJECT)`：状态 → `REJECTED` + `reject_reason=comment`（必填）→ `engine.reject(...)`。
- `Prescription_Cancel`：`cancel_reason` 必填 → 先按 **R-04** 判定：
  - `VOID_ONLY`：处方 → `VOIDED`；若存在 `PENDING` 的调剂记录 → **Dispense_CancelPending**（置 `CANCELLED`）；
  - `VOID_WITH_ROLLBACK`：处方 → `VOIDED`；调剂记录 → `CANCELLED`；**Herb_ReturnStock** 逐味按原调剂出库流水数量回冲（写 `biz_type=VOID_ROLLBACK` 正数量流水 + `stock_quantity +=` 原出库量）；
  - `BLOCK`：`raise ValueError("处方已发药，不可作废")`（状态不变）。
  - 前置（M2 v1.5）：状态 ∈ {DRAFT, PENDING_REVIEW, APPROVED, DISPENSING}（即「已发药/已作废」之外均可进入 R-04 分派；原前置漏了「已调剂」，会使 `VOID_WITH_ROLLBACK` 分支不可达）。

### 8.5 调剂链（`Dispense_Confirm` / `Dispense_Issue`）

- `Dispense_Confirm`：前置 `PENDING` + 处方 `APPROVED` + **R-02 全部充足** → 调剂记录 → `DISPENSED`（+`dispense_time` + `dispenser_id=当前用户`）、处方 → `DISPENSING`；联动 **Herb_DeductStock**：逐味 `stock_quantity -= singleDose * doses`，写 `biz_type=DISPENSE_OUT` **负数量**流水（`prescription_id` 必填，`quantity = -(singleDose*doses)`）；扣减后库存不得为负（REF-08）。
- `Dispense_Issue`：前置 `DISPENSED` → 调剂记录 → `ISSUED`（+`issue_time`）、处方 → `ISSUED`。

### 8.6 就诊与辨证相关规则

- `Visit_Register`：患者必须 `ACTIVE`；`visit_type=FOLLOW_UP`（复诊）时必须选 `previous_visit_id`；**主诉不由本环节录入**（M1 v1.5：`Visit.chiefComplaint` 必填口径归属接诊环节；若传值则 ≤200 字）；`visit_type`/`dept_code` 必须落在字典内。
- `Visit_Receive`：仅 `REGISTERED` 可接诊；**主诉必填且 ≤200 字（M2 v1.5：该环节负责录入主诉）**；`REF-05`：`receive_time >= register_time`（按时刻比较，M1 不变性原文）。
- `Visit_SaveFourDiagnosis`：仅 `IN_CONSULT` 可录；`pulse_code` 必填；同就诊唯一一份（更新语义）。
- `Visit_Cancel`：仅 `REGISTERED`/`IN_CONSULT`；**该就诊下不存在任何处方**；撤销原因必填（追加到 `remark`）。
- `Diagnosis_Save`：所属就诊**必须已有四诊信息**；`diagnosis_basis` ≥ 10 字；`DRAFT`。
- `Diagnosis_Confirm`：就诊必须为 `IN_CONSULT`；**INV-02 主证唯一**；治法必填 → `CONFIRMED`。
- `Prescription_Save`：就诊必须为 `IN_PROGRESS`（**M2 v1.5：处方状态为 `REJECTED` 时允许修改后重新提交，此时就诊已随提交收尾为 `COMPLETED`**）；**必须存在 `CONFIRMED` 的辨证结论**；剂数 1～30；明细非空、饮片不重复、单剂剂量 > 0。
